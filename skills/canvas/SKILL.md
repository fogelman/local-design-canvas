# Canvas

Canvas files belong to the project you're working in: create the canvas folder inside that repo (e.g. `docs/<topic>/canvas/`) and manage its files there. The canvas tool is only the server. Run `canvas [dir]` to serve a folder at http://127.0.0.1:4747. Every top-level `*.html` file is a live frame, and the viewer reloads it when the file changes. The user pins comments onto elements in the viewer.

## Answering comments (the main loop)

1. Run `canvas comments --dir <dir>`. It prints only the threads waiting on you, in compact form. A thread is waiting when it's open and its latest message was sent with "Send to Claude", shown as `@Claude`:
   `c4 login.html › main > form.card > button.primary "Continue"` and then the messages.
   Leave the other threads alone: people use them for notes to each other. `--open` lists every open thread, but only use it if the user asks.
   Do not read `comments.json` directly. The command output is the cheap view.
2. Open only the file the thread names. If the selector is `[data-cid="c7"]`, grep `data-cid="c7"` in that file, because it marks the exact element. Otherwise grep the quoted text. Keep `data-cid` attributes when you edit: they anchor the comment pins.
3. Make the change. Only when the comment is about how something looks (spacing, alignment, visual weight, "looks off"), run `canvas shot <id> --dir <dir>` before and/or after. It writes a PNG of that thread's frame, which you then Read. Skip it for copy, structure and data changes, because the image costs far more tokens than the text.
4. Run `canvas reply <id> "<one line: what changed>" --resolve --dir <dir>`. Leave `--resolve` off if you have a question instead of a fix.
   Handle several threads in a row, with one reply each.
   Threads on other pages print as `checkout/c2`. Pass that id as is, and the frame lives in `<dir>/checkout/`.

If `canvas comments` prints a `# <page>: Generated by …` line, those frames are build output. Make the change in the source it names, rebuild, then reply. Don't edit the generated html.

## Making frames

- Use one screen per file: `canvas new <name> [WxH] --dir <dir>`. Common sizes: 1280x800 (desktop) and 390x844 (mobile). The size lives in `<meta name="canvas:size" content="WxH">`.
- **Compose from components first.** If the canvas has `_ds/components/`, run `canvas ds --dir <dir>`: it lists every component (atoms → molecules → organisms → templates) with its usage line. Build screens as `<ds-index-page …>`, `<ds-data-table …>`, `<ds-button …>` instead of writing raw markup. The server expands them, so a screen stays a short, readable file.
  - Don't open component files to use them. The usage line is enough; open one only to change it.
  - When a pattern repeats on two or more screens, make it a component at the lowest level that fits, and give it a one-line `<!-- usage -->` header. Atom: a single element. Molecule: a few atoms. Organism: a section. Template: a page layout.
  - Component syntax:
    - `{{prop}}`, `{{prop|default}}`
    - `{{?prop}}…{{/prop}}`, `{{!prop}}…{{/prop}}` for optional parts
    - `{{@list:…$…}}` to repeat (items may be `Label:icon` → `$`, `$2`; `{{@list|A,B::…}}` gives a default; `$=active` marks the current item)
    - `<slot>` and `<slot name="x">`, filled by `<template slot="x">`
  - The project owns its components and usually installs them from its own repo. When you change or add one there, re-run the project's sync, or edit the copy in the canvas and port it back.
  - A comment inside a component prints as `⟨templates/app-shell › atoms/badge#3⟩`. Decide whether the comment is about the component (change it once and every screen follows) or about this one use (change the attributes or children in the frame), and say which in your reply.
- Design system: if the canvas has `_ds/ds.css`, link it, then read its header comment for the class list and use those classes and its CSS variables. Don't invent colours. The project owns `_ds/`: if the project offers a way to install or refresh it (for example a sync script in its docs), use that. Without `_ds/`, use one shared `styles.css`. Changing a css, js or image file reloads every frame.
- Link screens with plain `<a href="other.html">`. Interact mode and ▷ Play follow them like a prototype.
- Files starting with `_` or `.` are not frames, so use them for partials and data.
- Frames are plain static HTML, with inline JS only when the user needs interaction.
- Pages are subfolders (`<dir>/checkout/*.html`). Create one with `canvas new <name> --dir <dir>/<page>`.
- Never edit `canvas.json`. It holds frame positions, and the user moves frames in the viewer. New files are placed automatically.

## Starting it for the user (setup)

1. If the server isn't running, start it in the background: `canvas <dir> --no-open`, then give the user the URL. If the port is busy, it picks the next free one.
2. Run `canvas watch --dir <dir>`. If it prints `unset`, ask the user once, with the question tool: should you answer comments automatically as they arrive (watch), or only when they ask? Record the answer with `canvas watch on|off --dir <dir>`. It's saved in the canvas, so later sessions don't ask again. If it prints `on` or `off`, follow it without asking.

## Watching (only when `canvas watch` is `on`)

Run `canvas wait --dir <dir>` as a **background** command. It costs nothing while idle. It exits when comments sent to Claude arrive, waits a few seconds so a burst arrives as one batch, marks those threads as being worked on in the viewer, and prints them in the same format as `canvas comments`. When it exits, handle the batch as in steps 2–4 of the main loop, then start `canvas wait` in the background again.
- Don't poll, and don't use a fixed-interval loop.
- Keep going until the user says stop or turns it off (`canvas watch off`).
- While a wait is running, the viewer shows "Claude is watching".

With watching `off`, run `canvas comments` only when the user asks (e.g. "answer the canvas comments").
